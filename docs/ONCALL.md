# On-call: Daily E2E Watch and YouTube Flag Scan

After every run of the **Manual E2E** workflow (daily at 18:00 Warsaw time and on manual dispatch) an `oncall` job:

1. **Summarizes the results** — `scripts/oncall/summarize-results.mjs` reads the Playwright JSON report: failed, flaky, passed.
2. **Scans YouTube experiment flags** — `scripts/oncall/scan-flags.mjs`, keeping the flags that can touch the userscript. A flag is **relevant** when
   - its **name** matches our areas (`pip`, `miniplayer`, `cow`, `context_menu`, `watch_while`, `hotkey`, `shorts`, `speedmaster`, `popup`, `append_to`, …; `RELEVANT_FLAG_RE`), or
   - it is **checked next to code our flows go through**: within ~600 characters (about one minified function) of an anchor such as `yt-activate-miniplayer`, `ytd-miniplayer`, `SET_MINIPLAYER_IS_ACTIVE`, `enterpictureinpicture`, `documentPictureInPicture`, `setActionHandler`, `appendTo`, `ytd-player`, `ytd-shorts`, `ytp-contextmenu`, `ytp-bezel` (`CODE_ANCHORS`). This catches flags with unrelated names (e.g. `disable_theater_mode` next to mini player activation); each flag carries `why` (`name`, `near <anchor>`).

   Two scans:
   - **In the code (complete)**: every flag the Kevlar and player bundles check. The bundles are the same for every user, so this shows what YouTube prepares before it is rolled out to anyone (today ~1800 flags checked, ~140 relevant — ~120 by name, ~20 only by an anchor — most of them not served to a logged-out visitor). The flag-reading functions are minified differently in every build; they are recognized from the data (call targets whose string arguments are largely flags the page was served).
   - **Served (a sample)**: the flags this logged-out page got (page `EXPERIMENT_FLAGS`, player `serializedExperimentFlags`). YouTube buckets visitors randomly into experiments, so every load sees a different subset — this shows what is rolled out, never everything.
   - Some loads get YouTube's module-set loader (`ytmainappweb.base_module_set…/m=base`, ~1 MB, its code comes later in lazy modules) instead of the full Kevlar bundle (`ytmainappweb.kevlar_base…`, ~10 MB), which would show only a fraction of the flag checks: the scan loads the page again (a new random bucket) up to 4 times until it gets the full bundle, and says so in the error if it never does.
   - Both are compared with [`experiment-flags-baseline.json`](experiment-flags-baseline.json) (`codeFlags`, `flags`) and with flags already reported (GitHub Actions cache, saved only after the report went out), so each new flag is reported once.

3. **Probes new flags** — for up to 5 new relevant boolean flags, the `chromium` e2e set (9 tests) runs once with the flag forced to the opposite of its usual state (on if the page was not served it, off if it got true; `scripts/oncall/probe-flags.mjs`). A test failing only with the flag forced shows the flag breaks us; all green shows our flows survive it. Runs in the `flags` job on the CI runner; without new flags that job is only the scan. Flags over the limit are listed in the message ("⏳ Не прогнано тестами …") and stay new, so the next runs probe them (5 per run).
4. **Finds the flag culprit of failed and flaky tests** — `scripts/oncall/confirm-flag-culprit.mjs`, in the `flags` job. The e2e fixtures record the relevant boolean flags that were `true` for each failed attempt and for a passing retry and not forced by the project (`e2e/fixtures/page-flags.ts`, files in `e2e-results/page-flags/`). A logged-out context lands in a random experiment bucket on every load, so a flag may show up in one attempt only and a plain re-run proves nothing; instead:
   - **suspects** = flags on in every failed attempt, minus flags also on in the passing retry (a flaky test whose passing attempt had the same flags is not a flag problem);
   - the test re-runs with all suspects **forced on** (the failed attempt's state): passes → not reproduced by flags; then with all **forced off**: still fails → not the flags;
   - otherwise **bisect** (suspects on, half of them off) down to one flag, or the set that only fails together.

   Failed tests first, then tests carried over from earlier runs, then flaky ones; at most 2 tests per run (~log2(suspects) + 2 runs each, ~1 min per run on CI). Tests over the limit are **carried over** with their suspects (`oncall/pending-culprits.json`, kept in the Actions cache like the reported flags, saved only after the report went out) and checked in the next runs even if they pass there; a carried test is dropped after 7 days or when a newer run has fresh data for it. A carried result names the date of the run it came from, and a run with carried checks always sends a report. The result is a fixed line in the message, independent of Claude: "🎯 Прапорець-винуватець: <flag> — <test>: з ним падає, без нього проходить", "🔎 <test>: … — не прапорець", or "⏳ Не перевірено на прапорці" over the limit. To check a culprit by hand: `E2E_FORCE_EXPERIMENT_FLAGS=<flag>=false npx playwright test <spec>:<line> --project=<project>`.

5. **Investigates, only if needed** — when a test failed or was flaky, the results are missing, reading flags broke, or there are new relevant flags (in the code or served), Claude Code runs headless with [`scripts/oncall/investigate-prompt.md`](../scripts/oncall/investigate-prompt.md): it classifies each failure (our regression / YouTube change / environment) from the error, the mini player timeline, the userscript log and the page snapshot, and for each new flag reads its uses in the bundles and recommends ignore / watch / add to the e2e matrix / fix.
6. **Sends the finding to Telegram** in Ukrainian (`scripts/oncall/telegram-send.mjs`): the reason for the report, verdict, tests and flags with cause, evidence and what to do, the run link, and a line to continue in Claude Code. All green without new flags → no message.

**Broken flag reading always reaches Telegram**: the scan fails on purpose when no flags are on the page, a bundle is missing, no flag reader is found, or the code yields less than half of the baseline's relevant flags; a failed scan is a reason to report. If the on-call job itself breaks before a message went out, a last step sends "🔴 Онкол зламався" with the run link.

The artifact `oncall` of the run keeps `results-summary.json`, `flags.json`, the probe and culprit summaries, the report and the sent message. The full Claude transcript (`claude-transcript.jsonl`) is not an artifact (the repository is public and its tool results hold whole bundles and logs): it goes to the dev worker's private state bucket, `oncall/<run id>/claude-transcript.jsonl`, kept for `var.oncall_transcript_retention_days` (14) days ("Agent isolation" below).

## Continue in Claude Code

Every message ends with `Розбери онкол-прогін <run URL>`. Paste it into a Claude Code session in this repo: the run's artifacts (`oncall`, `e2e-results`, `playwright-report-manual-e2e`) hold everything the on-call saw (`gh run download <id> -n oncall`), and its transcript is in the state bucket (`aws s3 cp s3://<state bucket>/oncall/<run id>/claude-transcript.jsonl .`; `$STATE_BUCKET` in the dev worker, which fetches it together with the artifact when it loads a report).

## Runner and secrets

- **Daily start**: EventBridge Scheduler `youtube-pip-prod-oncall-daily` (`terraform/oncall_schedule.tf`; `var.oncall_schedule`, default `cron(0 18 * * ? *)` in `var.oncall_schedule_timezone` `Europe/Warsaw`, so 18:00 all year) invokes the Lambda `youtube-pip-prod-oncall-schedule` (`worker.schedule_handler` in `terraform/lambda/worker.py`), which dispatches `e2e-manual.yml` on `var.oncall_branch` with a GitHub App installation token (the app needs Actions: write). GitHub's own `schedule` trigger is not used: it started the run 2–6 hours late (the top of the hour is GitHub's busiest time) and stopped for good after GitHub disabled the schedule of this public repository for 60 days without activity.
- The job runs on `runs-on: [self-hosted, fargate, oncall]`. The dispatcher Lambda starts a separate, small task definition `runner-oncall` (1 vCPU / 2 GB) for it, with the secrets from AWS Secrets Manager **`youtube-pip-oncall`** (JSON: `claude_code_oauth_token`, `telegram_bot_token`, `telegram_chat_id`; optional `github_read_token`, a read-only token the dev-ops Lambda uses for the GitHub API) as `CLAUDE_CODE_OAUTH_TOKEN`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. The CI runner never gets them.
- The repository is public and any workflow file (also one changed in a pull request) could ask for the `oncall` label, so the Lambda checks the run through the GitHub API: only `schedule` / `workflow_dispatch` runs of `var.oncall_branch` (default `main`) of this repository get the on-call runner (`terraform/lambda/worker.py`).
- Claude Code runs isolated ("Agent isolation" below): it reads data downloaded from YouTube, which is untrusted. Model: `--model sonnet`, the alias for the latest Sonnet (updates by itself, never switches to another family); anything suspicious is investigated further by hand. Usage counts against the Claude subscription of `claude setup-token`, not AWS.

## Agent isolation

The investigation reads YouTube's bundles and pages, so a prompt injection there is part of the threat model. The runner itself holds the Telegram and Claude tokens (task environment), the ECS credentials of `oncall-task-role` and the job's GitHub token; the agent must reach none of them but its own Claude token, and nothing it writes may leak one. `scripts/oncall/run-agent.sh`:

- **Its own Linux user** `oncall-agent` (created by the job; the runner's user has passwordless sudo). The runner's processes run as another uid, so their `/proc/<pid>/environ` (the secrets, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`) is out of its reach, and the runner's home (the checkout with the job token, the runner's credentials, step scripts, `_temp`) is closed to others (`chmod 750`).
- **Not even the Claude token**: the runner's user runs the token proxy (`scripts/dev-worker/anthropic-proxy.mjs`; docs/DEV_WORKER.md, "Claude Code as a separate user"), which holds the real token and adds it to the agent's API requests. The agent gets only `ANTHROPIC_BASE_URL` and a placeholder that only this proxy accepts, through `sudo --preserve-env`: every other variable is unset, and nothing passes on a command line (`/proc/<pid>/cmdline` is readable by every user).
- **A copy to work on**: the repository at HEAD (`git archive`, no `.git`) and the on-call inputs (`oncall/`) in its own home; Claude Code (the native binary of the pinned npm package) installed by the runner's user, which the agent may run but not change.
- **Read-only tools**: `--tools Read,Grep,Glob` is the whole tool set it gets (no shell, network, edits, subagents, schedules or notifications; without it Claude Code also lists its other built-in tools, refused only by the permission mode); `--restricted` confines them to the working directory and ignores settings files of the copy, `--strict-mcp-config` drops MCP servers; reads of `/proc`, `/sys`, `/dev`, `/tmp`, `/home/runner` and its own Claude config denied on top ([`scripts/oncall/agent-settings.json`](../scripts/oncall/agent-settings.json)): defense in depth: its own environment holds only the placeholder.
- **Self-checks before it starts**: the step fails (and the message falls back to the raw results) when the agent can read the runner's checkout, the runner's or the task's environment, or has any credential but the proxy's placeholder in its environment (its token must be the placeholder, never the real one).
- **Output scrubbed and kept private**: the runner replaces any secret value of its own environment in the transcript and the report (`scripts/oncall/scrub-secrets.mjs`); the transcript goes to the private state bucket (the task role may only put objects under `oncall/`), never to the public artifacts.

## Operating

- **Test the pipeline**: run **Manual E2E** with `force_report: true` — investigates and sends a message even if everything passed.
- **Probe a flag by hand**: run **Manual E2E** with `probe_flags: flag_a,flag_b` (and `force_report: true` to get the message) — the `chromium` set runs with each flag flipped, new or not.
- **Test from a branch**: the Lambda only allows `var.oncall_branch`; for a test apply with `-var oncall_branch=<branch>`, dispatch the workflow on that branch, then apply again without it.
- **Rotate a token**: edit the secret `youtube-pip-oncall` in Secrets Manager; new tasks pick it up.
- **Too many flag messages**: flags are reported once (cache `oncall-seen-flags-*`). To accept the current set, regenerate the baseline: run `node scripts/oncall/scan-flags.mjs <dir>` a couple of times and put the union of the `relevant` names into `experiment-flags-baseline.json` (only observed flags: the ones we merely force in e2e are not served to logged-out pages and would show up as "gone").
- **Pause**: disable the **Manual E2E** workflow (`gh workflow disable e2e-manual.yml`).

## Claude Code updates

Claude Code is pinned in two places: the dev worker's Agent SDK (`scripts/dev-worker/package.json`, which bundles the CLI) and the on-call investigation (`scripts/oncall/run-agent.sh @anthropic-ai/claude-code@<version>` in `e2e-manual.yml`). A pin keeps the integration stable, but an old version can stop working against the API (server-side minimum versions per model, retired models), so a weekly job keeps them current, with the owner deciding.

- **Trigger**: EventBridge Scheduler `youtube-pip-prod-claude-code-update-weekly` (`var.claude_code_update_schedule`, default Monday 21:00 in `var.oncall_schedule_timezone`) invokes the on-call scheduler Lambda with `{"workflow": "claude-code-update.yml"}`; it dispatches the workflow on main. Also runnable by hand (`force` re-runs the checks on the current versions).
- **Detect** (`scripts/claude-update/versions.mjs`): the newest SDK and CLI on npm against the pins; nothing to do when they match or a `deps/claude-code-<version>` branch exists (its PR waits for the owner).
- **Check** (on the `oncall` runner: the Claude token, cheapest model): worker unit tests; the SDK contract smoke test (`scripts/dev-worker/sdk-smoke.mjs`: init, permission callback allow / deny, AskUserQuestion answers, permission mode status, models, background task events, rate-limit event, resume with `CLAUDE_CODE_TRANSCRIPT_LOCAL_GC`, and what `/agents` uses: a subagent's text streamed with `agent_id`, `getSubagentMessages()`, the Agent tool's result); the worker end to end with a fake AWS / Telegram and the real Claude (`scripts/claude-update/worker-e2e.sh`); the on-call CLI in print mode. On the update PR, `dev-worker-image.yml` builds the image and runs the isolation check (Claude Code started as `worker` through `spawnClaudeCodeProcess`); the worker end to end here runs without `CLAUDE_USER`.
- **Green**: `scripts/claude-update/open-pr.mjs` commits the bump and opens a PR as the GitHub App (a token narrowed to contents, pull requests and workflows of this repository, from the on-call scheduler Lambda's `app_token` action: a PR opened with `GITHUB_TOKEN` would start no checks), and Telegram gets `🆕 Claude Code <version>: tests green, PR …`. After the owner merges it, `dev-worker-publish.yml` (push to main changing the worker's `package.json` / lock) waits until the public API shows the commit and asks the dev-ops Lambda to publish the worker image: the owner gets the usual ✅. The on-call uses the new CLI from its next run.
- **Red**: Telegram gets `🔴 Claude Code <version> breaks our integrations` with each check's outcome and the run link (hand it to the dev worker to investigate); the pins stay. A failing version is tried again the next week (until a newer one comes).
- **Rights**: the on-call runner tasks run with their own role `youtube-pip-prod-oncall-task-role` (dispatcher: only `schedule` / `workflow_dispatch` / `push` runs of main get them), which may invoke the on-call scheduler and the dev-ops Lambdas and put the on-call agent's transcripts into the state bucket (`oncall/`) only. The on-call scheduler's GitHub App (the runner App) needs Contents, Pull requests and Workflows: read and write.
