Fast lane and worker: hand-over and shared state

How a task crosses from the Lambda to the ECS worker, and how the two parts stay one assistant through S3. Which part gets a message: the message flow diagram.

A hand-over: only dev-bot writes the worker's queue and starts the worker

⚡ Fast lane

hand_over a task, stop_worker, a setting or a /background stop for the worker.

After web or log text in the turn: only after the owner's button.

→

🗄 S3 fast-lane/handover/<uuid>.json

The task with its reason and date, or control.

Only the fast lane's and the worker task's roles can write there.

→

🤖 dev-bot {"action": "hand_over", "key"}

Reads the object once and deletes it; refuses one older than 10 minutes.

The invocation names only the key: anyone may invoke dev-bot.

→

🛠 Worker queue

A task: says it in the chat, starts a sleeping worker.

A stop, /compact or a setting: only to a running worker, never starts one.

One answer per message: when every message of a turn was handed over, the fast lane sends no text of its own and the worker answers.

Two-way sync: built by code before every prompt, never by the model

⚡ Fast lane learns

A [Worker note] in front of each prompt: the worker's real state (starting, free, busy with which step, waiting for the owner, stopping, stopped), its PRs and runs, what the owner and the worker said since the fast lane's previous answer, new on-call reports, the owner's local time.

A new session also gets the memory index and the plan titles.

🛠 Worker learns

A note at the start of its next turn: the owner's messages the fast lane took and its answers since the worker's previous turn (what it said, scheduled, cancelled or set).

A setting changed in the fast lane arrives at once as a control message, applied to the live session without a model turn.

Files both parts write use conditional writes (ETag, read-modify-write retried on a conflict), so neither part drops the other's change.
